# Native durable harness

`github.com/rcarmo/go-ai/durable` persists provider → owned host tool → provider answer runs in a native memory store or append journal. The useful M1 runtime is independently accepted and published in [native v1.0.1](https://github.com/rcarmo/go-ai/releases/tag/v1.0.1) and [upstream-v1.0.1](https://github.com/rcarmo/go-ai/releases/tag/upstream-v1.0.1), both targeting `33fcb88e6d9d5996279cd6f88687f988728aa2d8`. The working tree aligns the audited pi-durable 1.0.4 deltas and passes minimum-toolchain, race, static and local public-consumer checks. [1.0.4 validation](../v104/local-validation.md) records polling/argv/PowerShell, host-store, decoder and platform boundaries. The earlier 1.0.0 [parity closure](parity-closure.md) retains its version scope. Rui authorised the native v1.0.4 commit/tag/publication cycle on 6 October 2026; [release audit](../../RELEASE.md) records its outcome. Independent blanket TypeScript replay and external clean-clone acceptance have not been performed.

## Run the local example

```sh
go run ./examples/durable
```

The example starts a local fake OpenAI HTTP/SSE server, registers a replay-safe sum tool and uses the exported `goai.Stream` provider path. It prints `The sum is 5.` without live credentials or an external server. Set `DURABLE_EXAMPLE_DIR` to retain its journal; the same request ID returns its stored answer on later runs.

## Public API

```go
store, err := durable.OpenJournal(dir, durable.JournalOptions{}) // Sync=true
registry := durable.NewRegistry()
err = registry.Register(durable.ToolRegistration{
    Definition: tool, Implementation: "host.sum", Version: 1,
    ReplaySafe: true, Execute: execute,
})
h, err := durable.Open(ctx, store, durable.Options{
    Models: resolveModel, Registry: registry, RequestOptions: resolveAuth,
})
root, err := h.Root(ctx, durable.AgentChange{Model: modelRef})
sub, err := root.Submit(ctx, durable.Input{Content: "hello", RequestID: "request-1"})
settled, err := sub.Wait(ctx)
err = h.Close(ctx)
```

`SubmissionHandle.Status` exposes `queued`, `placed`, `done` and `unanswered`, with input/answer entry IDs. Idle input is placed atomically at admission. `Abort` withdraws queued input or writes and reports already-placed or settled work; `AbortSubmission` may scope lookup to a conversation. `Wait` returns the native compatibility envelope plus the same public lifecycle in `Settlement.Record`. Invocation-bound operations run under the task's context and lose authority when the invocation ends. Raw transaction `CreateSubmission`, `PlaceSubmission` and `SettleSubmission` resolve the latest staged record and preserve the first terminal settlement.

Harness `Commit`, `TypedEntry`, typed document reads/state/watches and `SubscribeCommits` forward the Session surface without duplicating storage logic or enabling scheduling.

Callers must check every error. `Open` adopts/reconciles committed state but starts no external effects. `Submit`, `Resume`, `Wait` and `WaitForIdle` may schedule pending work. Wait cancellation affects that waiter only. `RootWithInit` applies the root agent and initializer in one commit; an existing root ignores both supplied changes and initializers. `ConversationHandle.Commit` binds task creation to its conversation and accepts passive changes while work is live; it does not enable scheduling. Harness-created raw conversations initialise their built-ins and agent even without a creation callback. Plain Session-created conversations remain document-free; agent and context getters resolve defaults without writing. `Abort` commits cancellation marks before signalling and draining tools; child terminal receipts precede parent cleanup. `Close` fences new admissions and joins providers/tools and admitted commits, including noncooperative host code. A cancelled Close wait never releases storage ownership early or invents an aborted outcome.

Tool definitions are copied and the offered set is pinned with each request. Each tool has a distinct durable task ID and parent Owner; provider call IDs are transcript identifiers only. Arguments are bounded strict JSON, validated/repaired before intent, and the final execution arguments and implementation/version/replay policy commit before Execute. The assistant entry and successor model context keep the model's original call arguments; repaired arguments live separately in the owned tool checkpoint. Unconfirmed execution intent repeats preparation and validation; confirmed safe execution replays without preparation.

`ToolAPI.Output` commits bounded progress, never raw volatile output. Defaults are 50KiB and 2000 lines with head truncation. Returned content replaces progress; omitted content/details inherit it. Explicit details replace progress and may be any JSON value. ToolResult content/details/validated usage and its application-document Commit callback adopt atomically with the tool result. Valid usage appears in both the result entry/checkpoint receipt and the same-commit `pi.usage.tools` aggregate, including error/aborted outcomes. Invalid returned data, including usage counters/costs, faults without a tool receipt or application mutation; continuation synthesises a missing result. Valid billed error usage is retained once. Thrown tool errors retain partial output and the original diagnostic; the failed task outcome is `Tool <name> threw`. `afterTool` may replace the result, including its error flag, without changing that failed task outcome. Private environment callback payloads are reported locally and excluded from durable state. Application callbacks may mutate conversation-scoped non-`pi.*` documents only. Returned/escaped ToolAPI writes reject after invocation; Set/Update detach before returning. Credentials, headers, executable hooks and endpoint resolution stay process-local. The host must avoid putting secrets in application JSON, text or details. Assistant protocol signatures, response IDs and provider error messages are retained. `Read` follows reference text/image rejection and continuation diagnostics; `ReadWithImages` is an explicit native extension. Bash has no default timeout, uses a tail output policy and publishes spill diagnostics before failure.

## Validation and replay

The enforced schema subset supports explicit object/array/string/number/integer/boolean/null types, object properties/required/boolean additionalProperties, arrays with one item schema/minItems/maxItems, strings minLength/maxLength/Go RE2 pattern, numeric minimum/maximum and typed enums. Numbers are bounded to the exact `2^53−1` range; comparisons use exact decimal rationals with bounded spelling/exponents, so near-ceiling fractions never become integers through float rounding. Unsupported/malformed schemas reject at registration unless an explicit strict host Validator owns unsupported keywords; root tool arguments remain objects. This is not full JSON Schema/TypeBox validation.

Unsafe replay is the default. An interrupted started tool runs again only when stored and current ReplaySafe are true. Stored unsafe/current safe cannot upgrade an old intent. Implementation-ID equality is not a replay gate. Missing started tools settle with an `interrupted` receipt; unavailable unstarted calls complete with `tool_unavailable`. Replay-safe effects can occur twice after uncertain remote/outcome failure; host idempotency remains necessary. Terminal committed outcomes never rerun or double-count known usage.

Model requests pin sanitized model behaviour, settings and context cutoff; local endpoint/authentication refresh on dispatch. Durable retries return to preparation and reread committed agent, tools, prompt and settings. Each failed attempt appends its assistant receipt. Retry/compaction policies resolve after the response; `SetSettings` replaces host settings atomically for future resolutions. Terminal identity and spend use the pinned model. Payload rewrite hooks and unpinned behaviour options, including non-nil RetryConfig hidden by `json:"-"`, reject before intent/effects. Process-local read-only observers remain host code; no purity guarantee is supplied. Deferred response polling uses committed checkpoints; request hooks are not repeated for each poll. Providers decide handle expiry. A thrown polling callback faults the task without inventing an assistant receipt. Model requests can be billed again after an uncertain remote outcome; usage that never reached a durable receipt can be unknown.

## Storage and scope

The journal is native GODJNL1 framing, not upstream JSONL/SQLite interoperability. Default Sync=true; owner-only directory/file, strict JSON, durable ID reservations, coherent persisted resource caps, legal final torn-tail truncation and fail-closed complete corruption. Uncertain append/sync poisons reads/dispatch until close/reopen. Power-loss guarantees depend on filesystem/device semantics. In-process exclusivity is enforced; cross-process exclusivity and path replacement exclusion are host preconditions. Journal and SQLite reclamation preserve logical history. SQLite uses a cooperating-process ownership lock; journal cross-process exclusion remains a host precondition. Encryption and a hard RSS bound are not supplied. See [package format/limits](../../durable/doc.go).

The local native history/definition/delta checkpoint adds fork ancestry, half-open document incarnations, as-of/current copies, lazy migrations and decoded delta/checkpoint selection. These slices and their integrated durable regression are independently accepted. The current working tree also passes the final repository and durable/tools race gates; no successor publication was made. Generic tasks, extensions, subagents, adaptive progress, committed views/events/task graphs, steering/reset boundaries, compaction, deferred polling/retries, SQLite/reclamation and coding tools are implemented locally. Current assertions, native adaptations and verification limits are listed in [parity closure](parity-closure.md). Unprovable legacy-agent history is rejected instead of backfilled. Built-in tools are host callbacks; the package does not silently run bash or access files.

## Agent selection and task phases

`Configure` retains replacement semantics. `ConfigurePatch` changes supplied fields and clears optional fields by name; an absent model admits input and settles it with the reference no-model failure. Agent extension/tool arrays preserve explicit order, filters edit live defaults, and `Options.Extensions` selects host defaults by installed name. Pure tool/section wrappers run after all selected declarations compose and before tool filtering. Errors, panics and renamed targets remove only that target and report outside registry locks. `Uninstall` matches extension names; individual registration disposers remain identity-fenced so disposing an old registration cannot remove its replacement.

`TaskRuntime.Agent(ctx)` resolves lazily from the phase's captured registry and configuration committed before first use. The result or failure stays cached until the next phase; each caller gets detached data. Cancelling one caller leaves the shared resolution intact, and phase/Close joins retain ownership of any in-flight wrapper callback. `Extension.TaskHooks` registers named custom handlers for a task kind; `TaskRuntime.EachHook` visits selected handlers in extension order using the same phase cache. Handler/callback failures are reported and later handlers continue unless the invocation is cancelled. Inputs and results cross the strict detached JSON boundary; escaped handlers reject after invocation end.

`TaskRuntime.Environment` resolves a fresh process-local environment with the current committed cwd at every use. `ConversationHandle.Agent` reads current configuration and registry selection without writes or enabling scheduling; invocation-bound handles lose read authority when their task invocation ends.

Tool recovery resolves the current committed agent/cwd. Replay requires both stored and current safety; implementation/schema identity equality is not a replay gate. New scheduler fault/orphan tool outcomes retain no tool receipt; context derivation supplies `missing_result` to the provider after owned work and actual hosts drain. Older stored scheduler cleanup records keep their legacy receipt semantics. Native invalid-result fallback and unavailable-tool error codes are separate compatibility boundaries.
