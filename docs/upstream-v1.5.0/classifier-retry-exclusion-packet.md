# Classifier retry exclusion wiring

At upstream `f9a26365568127461c47a07a37dcb42c140a3ac5`, `packages/ai/src/api/openai-decisions.ts` passes `[504]` to `postClassifierRequest`; `system-one-shared.ts` passes no exclusion. `classifier_decisions.go` passes `[504]` and the Go classifier HTTP adapter excludes it from its retryable status list. The upstream Decisions test expects one 504 request with a gateway message that omits HTML and a successful retry for 503.

The existing `TestDecisions110GatewayNoRetryOtherRetriesCancelTimeout` exercises those 504 and 503 outcomes, 401 error content, cancellation and timeout. The new production-path `TestMainDecisionsProviderExcludesGatewayTimeoutDespiteRetryHeader` adds a 504 with `X-Should-Retry: true`; it expects one request and the same gateway error behaviour. This is a source-derived precedence control, not a literal upstream test. Both functions passed count1 in 0.045s. A temporary overlay removing the Decisions 504 exclusion made the new control fail with three requests. `go vet . ./tests`, formatting and `git diff --check` passed with `CGO_ENABLED=0`; overlay scratch was removed. No runtime change was needed.

The native status-list adaptation currently limits its generated 5xx list to 500–599 and always includes 408, 409 and 429. The pinned Decisions caller excludes only 504, so those generic differences are outside this control. Full classifier and provider retry parity, the full suite, profiling, hosted CI and release remain unverified.

At parent `432ca57`, the Decisions allow-list returned immediately for status 600 and for status 400 with `X-Should-Retry: true`; both conflict with the pinned generic classifier. The source-derived `TestMainDecisionsProviderRetriesServerStatusesAndDirective` failed both cases before the change. The adapter now passes exclusions to a private HTTP retry path after normal retry classification, preserving the original final response and body for excluded statuses. Existing public `RetryConfig.RetryableStatuses` semantics remain unchanged. Both new cases and the existing 504, 503, cancellation, HTTP ownership and retry-header controls pass count1. Overlays restoring the parent classifier and removing the exclusion each failed their respective controls. `go vet . ./tests`, formatting and `git diff --check` passed with `CGO_ENABLED=0`; scratch was removed. Classifier default retry count and other callback/timeout behaviour remain open.

At parent `265fc81`, the pinned Decisions 503 recovery with omitted retry options failed after one request; upstream defaults to two retries. The llama.cpp classifier uses the same upstream default. Go now defaults to two retries and a 60-second server delay cap. Non-zero legacy integer fields remain supported; `MaxRetriesOverride` and `MaxRetryDelayMsOverride` distinguish explicit zero from omission and take precedence over those fields. This changes zero-valued options from no retries to the upstream default. Callers requiring no retries must set `MaxRetriesOverride` to a pointer to zero; callers requiring an unlimited server delay must set `MaxRetryDelayMsOverride` similarly.

The Decisions default recovery and explicit-zero production controls, six configuration cases, provider HTTP controls and five System One/llama.cpp classifier controls passed count1. A zero-default implementation fault failed the recovery control. A separate parent-source overlay could not compile after the new API was added; the pre-change baseline above is the behavioural evidence. `go vet . ./tests`, formatting and `git diff --check` passed with `CGO_ENABLED=0`; scratch was removed. Timeout and request-cancellation equivalence remain open.

At parent `bc9b1e5`, an attempt with `TimeoutMs: 20` and two retries made three requests. Pinned `classifier-shared.ts` converts the attempt timeout to a `TimeoutError`, which the provider-error guard does not retry; `llama-cpp-classify.ts` has the same structure. Classifier HTTP calls now return Go timeout errors directly rather than classifying them as retryable status-zero provider errors. This applies to Go `net.Error` timeouts, including transport timeouts; it is a Go adaptation that is broader than an explicitly fired JavaScript timeout signal. Caller cancellation still takes precedence in the retry loop.
