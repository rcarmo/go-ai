# Durable turn limits apply after a completed tool round

Four original `harness-turn-limit.test.ts` cases ran unchanged after byte verification of the fixture, agent and generation sources, support and runner inputs. Six existing Go groups passed twice on the unchanged native base. The new projection did not compile without `MaxTurns`; with configuration alone, all three live SQLite cases wrongly settled `done` instead of `unanswered` with `turn_limit`.

The optional positive integer uses the existing `pi.agent` configuration record. A patch can remove it; caller pointers are not retained. The scheduler checks the limit after completing a tool round and uses the existing failed-run settlement. It keeps task ownership, completed generation status and the tool-result transcript. It does not report a task fault, migrate data or change the checkpoint shape. A yield continuation starts a fresh count. The held-round case changes the limit in flight and proves the change takes effect at the round boundary.

All four matched Go cases and both surrounding focused groups passed on repeat. Compiled controls caught an off-by-one cap, an omitted yield reset and an omitted clear. Vet and Staticcheck passed. An existing section-order test failed intermittently on both the candidate and an exact baseline overlay (three of 12 baseline attempts); no section-order change is included. Fractional and nonfinite `maxTurns` values and JavaScript `RangeError` identity are not representable by the typed Go API. The separate restart, inheritance, joined steer and terminate-at-cap cases are not covered by this receipt.
